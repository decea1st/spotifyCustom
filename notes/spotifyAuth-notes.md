# Notes on `spotifyAuth.ts`

## Why logging in with a Spotify account in MY app is tricky

Normally, when I register an app I make to Spotify's developer dashboard, I am given a `CLIENT_SECRET` by Spotify which is used to verify that login requests are truly coming from **MY APP** and not some random user's terminal.

So this is what would happen:

1. Browser sends user to Spotify to log in
2. Spotify redirects back with `?code=AQD8x...` or something
3. Browser hands the code to my server
4. My server calls Spotify's token endpoint with `code` + `client_id` + `client_secret`
5. Spotify checks the secret matches, returns an access token

The code and `client_id` are public, they can be stored anywhere. But the secret can't be public since it can be used along with the other two codes to pretend like endpoints being hit are coming from my app. Normally the secret would be added from my app's backend server and sent directly to Spotify's server through an HTTP request body so no one else sees it.

My app is a **BROWSER app**. It doesn't have a backend to store secret variables that a client isn't supposed to see. They can just use devtools to see the `CLIENT_SECRET` and leak it.

> Since a browser app simply can't hold a secret at all, this method just needs to be abandoned. This is where a PKCE verifier comes in.

---

## The PKCE flow

### Setup (one time)

I register my app on Spotify's dashboard. I get a `client_id` and set a redirect URI (e.g. `http://localhost:5173/callback`). Spotify will only ever redirect to URIs I registered — a separate protection that matters here.

### 1. User clicks "Log in with Spotify"

My app generates a fresh random verifier:

```
aB3xK9pQ...7fT     (64 chars)
```

It hashes it:

```
challenge = sha256(verifier) → base64url → "LPJNul-wow4m..."
```

and stashes the **verifier** in `sessionStorage`. The verifier stays in the browser and goes nowhere yet.

### 2. User is sent to Spotify with the challenge in the URL

```
https://accounts.spotify.com/authorize
  ?client_id=a3f9c2...
  &response_type=code
  &redirect_uri=http://localhost:5173/callback
  &scope=user-read-private user-top-read
  &code_challenge_method=S256
  &code_challenge=LPJNul-wow4m...
```

The browser physically leaves my site at this point, and Spotify files the challenge against **THIS** pending login.

### 3. User logs in on Spotify's domain

The user is now on Spotify's domain, seeing Spotify's own login page. My app is not involved and never sees their password.

So all I've done at this point is give my client a hashed code made from a random verifier that stayed on the client's device, and sent them to Spotify's OWN login page so Spotify can file this hashed code against THIS login request.

### 4. Spotify redirects back

```
http://localhost:5173/callback?code=AQD8xR2...
```

A random code generated by them, in the URL, which acts as proof that the user was able to successfully log in.

My app loads fresh. It receives this code. Everything in memory from step 1 is gone — **this is why the verifier went into `sessionStorage`**, which survives the round trip. My app reads this code from the URL and the verifier back out of storage.

I still don't have an access token.

### 5. POST to Spotify's token endpoint

Sending the code back proves the user successfully logged in. Sending the verifier proves this is the same party that sent the hashed code earlier (Spotify runs the same hash on it and matches). An attacker has had no way of receiving this verifier up to this point. The POST happens over TLS, which is not leaky like a code in a URL.

```
POST https://accounts.spotify.com/api/token

grant_type=authorization_code
code=AQD8xR2...
redirect_uri=http://localhost:5173/callback
client_id=a3f9c2...
code_verifier=aB3xK9pQ...7fT     ← the raw verifier, first time it's sent
```

Spotify hashes the verifier, compares it to the challenge it filed in step 2, matches it. My app gets:

```json
{
  "access_token": "BQC4y...",
  "refresh_token": "AQBv1...",
  "expires_in": 3600
}
```

Then: clear the verifier from storage and strip the code from the URL. Both are single-use and spent.

### 6. Use it

```
GET https://api.spotify.com/v1/me/top/tracks
Authorization: Bearer BQC4y...
```

The access token dies after an hour. The refresh token buys me a new one without sending the user through the login again.

---

## How an attack gets stopped

The code in step 4 sits in the URL bar, browser history, maybe an extension's reach. **Assume it leaks.** An attacker replaying it hits step 5 without a verifier. Spotify's hash comparison fails, no token.

The verifier never traveled over the network until step 5, and never in a form anyone could read from the outside.

## What the code does

### `generateCodeVerifier` — random alpha-numeric string of length 64

```ts
const values = crypto.getRandomValues(new Uint8Array(64));
```

- `Uint8Array(64)` creates an array of 64 elements
- **u** → unsigned, so no negative numbers
- **int** → integers
- **8** → 8 bits per slot, so 0–255 in decimal per slot

When `getRandomValues` is handed this array, it modifies it **in place**, replacing each slot with a cryptographically random number.

```ts
values.reduce((acc, x) => acc + possible[x % possible.length], "")
```

`reduce` takes a callback function and a string as its parameters. The empty string is the first input for `acc`. The callback function is run on **EACH** of the array's elements and the output is the new `acc` for the next run.

Here the callback takes the current element from the array, uses that along with mod to select a random character from `possible`, then appends that to the given string. The output is eventually a random alpha-numeric string of length 64.

### `hashCodeVerifier` — the hashing process

**1. Text → bytes**

```ts
const encoded = new TextEncoder().encode(plain);
```

Convert the plaintext to each character's byte version. Each byte is placed in a slot of an array. Required because crypto functions work on bytes, not text.

**2. Bytes → hash**

```ts
const hashed = await crypto.subtle.digest("SHA-256", encoded);
```

SHA-256 always outputs exactly **32 bytes** no matter how long the input is, and with a `Uint8Array` each slot is 1 byte, so the output is an array of 32 slots with each slot having a number from 0–255. It looks like the same *kind* of thing as the input — an array of bytes — but the numbers are unrelated and the length is always 32.

**3. Hash → string**

```ts
const tempString = String.fromCharCode(...new Uint8Array(hashed));
```

This array needs to be converted back to a string. The important thing is that `digest` returns an **ArrayBuffer**, which is a memory block that can't be indexed into. That's why `hashed` is passed into `Uint8Array()` — it turns the memory buffer into a real, indexable array.

`...` spreads the array into separate arguments, so instead of `fromCharCode([44, 242, ...])` you get `fromCharCode(44, 242, 77, ...)`, which is what it expects.

The output will be a string of text, but with random characters and artifacts, not just safe alpha-numeric characters.

**4. String → Base64**

```ts
btoa(tempString)
```

Converts the text into Base64 — still a string, but only `A-Z`, `a-z`, `0-9`, and `+`, `/`, `=`.

**5. Base64 → Base64URL**

```ts
.replace(/=/g, "")     // padding, unnecessary
.replace(/\+/g, "-")   // + means "space" in a URL
.replace(/\//g, "_")   // / is a path separator
```

`+`, `/`, and `=` all mean something else inside a URL, so they'd get mangled in transit. This step is **not cosmetic** — the challenge goes to Spotify as a query parameter, so skipping it breaks the auth request.

Now my app has the challenge that gets handed to Spotify when the user is redirected to their auth domain.
